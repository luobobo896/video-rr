# 要不要换 PostgreSQL？—— 基于线上真实数据的判断

> 结论先行：**现在不换。** 线上库 `app.db` 417 KB、`play_events` 266 行、`orders` 15 行，
> 离 SQLite 的天花板还有三个数量级。真正该先做的是「埋点补全 + 每日汇总表 + 可靠备份」，
> 这三件事各半天，收益比换库大得多。换库放到 DAU 过 5000 或需要多实例写入时再做。

## 二、埋点补齐后的容量测算

补上曝光/详情/付费墙/完播/搜索后，事件表按最坏情况估：

| 假设 | 事件量 | 年增量（行宽 ~120B + 索引） |
| --- | --- | --- |
| DAU 500，人均 20 次浏览/播放 | 1 万/天 | ≈ 365 万行 / 年，约 0.6 GB |
| DAU 1000，人均 30 次 | 3 万/天 | ≈ 1100 万行 / 年，约 1.8 GB |
| DAU 5000，人均 30 次 | 15 万/天 | ≈ 5500 万行 / 年，约 9 GB |

写入并发（SQLite 是单写者，WAL 下写不阻塞读）：

- DAU 1000 / 3 万事件 = **0.35 写/秒**；即便晚高峰集中 1 小时，也就 **8 写/秒**。
- SQLite 单机持续写入能力在千级/秒，本机 loopback 读压测已到 1.1 万 req/s。

**结论：单机 SQLite + WAL 能撑到 DAU 数千、事件千万级。**

## 三、真正该换库的四个信号

1. **要多台应用实例同时写**（SQLite 写锁不出主机）→ 现在是一台 HK，nginx 反代单进程。
2. **需要时间点恢复 / 行级权限 / 逻辑复制**（老板或财务要求可追溯、可回滚到任意时刻）。
3. **分析师要在线上跑重查询**（窗口函数、留存、同期群），且不愿用离线副本。
4. **事件表要做 JSONB 深查询 + 物化视图**（SQLite 有 json1 与窗口函数，但表达力和并发隔离弱）。

目前 1 不需要、2 可以用更好的备份方案替代、3 可以用汇总表替代、4 用不到。

## 四、换库的代价（如果坚持现在换）

| 项 | 内容 | 工作量 |
| --- | --- | --- |
| 适配层 | `server/database.mjs`：把 `db.prepare(sql).run/get/all` 映射到 `pg`，含事务 | 0.5 天 |
| SQL 改写 | `?`→`$1`；`datetime('now')`→`now()`；`INSERT OR IGNORE`→`ON CONFLICT DO NOTHING`；`AUTOINCREMENT`→`GENERATED BY DEFAULT AS IDENTITY`；`date(x)`→`x::date`；`RANDOM()`→`random()`；`lastInsertRowid`→`RETURNING id`（约 700 处） | 1 天 |
| 依赖 | 引入 `pg`（**打破当前零依赖**），`install-hk.sh` 里装 PostgreSQL 16 + 建库建角色 | 0.5 天 |
| 数据迁移 | `sqlite3 app.db .dump` → 改写 → `COPY`；校验行数与金额合计 | 0.5 天 |
| 回归 | 78 项单测 + 79 项端到端 + 28 项线上验收全部重跑 | 0.5 天 |

合计约 **2 天**，且必须在 HK 上真跑一遍才能上线。

## 五、现在就该做的三件事（比换库优先）

1. **每日汇总表**：`daily_stats(day, plays, viewers, detail_views, paywall_views, orders, paid, revenue)`，
   每天 03:10 由定时任务写一次，后台报表一律读汇总表，明细表只做归档。
2. **可靠备份**：现在 `install-hk.sh` 是 `cp app.db`（连同 `-wal`），WAL 模式下仍有撕裂风险；
   改用 `sqlite3 app.db ".backup 'backup/app.db.<ts>'"`（在线一致性备份），或上 litestream 同步到对象存储。
3. **事件表按月分表**：`track_events_202611` 这类后缀，脚本切月建表，报表用 UNION 视图；
   单表永远不超过千万行，查询与归档都简单。

## 六、如果以后确定要迁，最省事的路径

**双写过渡**：业务表继续 SQLite（事务、支付、权益判定都在这里，风险最高、动它收益最低），
事件表（`play_events` / `track_events` / `security_events`）改写到 PostgreSQL，
后台统计只读 PG。这样只改 `analytics.mjs` 的写入与报表 SQL，不碰任何交易链路，
可以先用一个月验证 PG 的表现再决定要不要整体迁。
