# ADR-0001：游客支付后自动建号与登录

状态：Proposed

## 背景

游客 15 秒试看后可直接付费，但当前 `orders.user_id` 非空，支付和权益都绑定登录用户。需求还要求自动生成账号密码，且邮件不能是唯一登录方式。

## 决策

- 游客开始收银时创建 `pending` 用户，生成唯一用户名和随机密码；订单绑定该用户。
- 支付成功回调激活用户、发放权益，并生成一次性 `claim_token`。
- 客户端通过游客订单 token 轮询，支付成功后兑换 `claim_token` 获得 session。
- 明文密码只在支付成功页展示一次，不入库、不进日志、不发明文邮件。
- 新增用户名 + 密码登录；邮箱登录保留为已绑定用户的第二方式。
- 用户名格式 `mh` + 10 位小写字母/数字；密码 12 位随机字符。

## 替代方案

1. **orders.user_id 可空，支付成功后再建号**：语义更干净，但 SQLite 需要重建订单表，支付回调与权益发放改动更大。
2. **只发邮件临时密码**：不满足“邮件不是唯一登录方式”，且存在明文凭据泄露风险。
3. **支付成功页让用户自己设置账号密码**：转化多一步，且支付后用户可能直接离开。

## 后果

- 未支付会留下待激活账号，需要 24 小时清理任务。
- 用户名登录、claim token、游客订单轮询都需要新增限流和测试。
- 账号合并先不自动化；已登录用户支付仍走现有流程。
- 退款保留账号，只回收权益。

## 复审条件

- 游客支付转化率证明待激活账号清理成本可接受。
- 需要支持手机号/第三方登录时，重新评估账号标识和合并策略。
